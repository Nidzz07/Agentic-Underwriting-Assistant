## 2. The dual-read double, the master-detail machine, and the separation teeth — made testable (the addenda)

`ui-history` is the **first** UI unit with **two read operations in one seam** (R6 list + R7 by-id), the **first** to render **both** namespaces, and the **first** with an **in-unit master-detail** navigation. Four things the NFR set must pin:

- **(a) The dual-read double (Q1).** Both operations are **reads**, so — unlike U7/U8's asymmetric read+write double — there is **no "zero write calls before confirm" teeth**. Instead the load-bearing count teeth are **read-attribution** (a row select → exactly one `fetchDetail`, zero `fetchList`; a page change → exactly one `fetchList`, zero `fetchDetail`; **Back → zero new `fetchList`**, T13) and **retry-targeting** (listError→lastPage, detailError→sameId, T10). Q1 pins the double's shape (single seam exposing two independently-capturing spies vs two separate doubles).
- **(b) The separation teeth (T2, the load-bearing target).** As with `ui-memo-view`'s SEPARATION-1, the proof is a **direct DOM-tree containment assertion** (real teeth: query both region nodes and assert non-containment + namespace exclusivity), not mere testid presence. `Node.contains()` is implemented in **jsdom** and returns `true` for any descendant at arbitrary depth — so the non-containment check is sound. The user pinned this construction (DOM-containment, mirroring SEPARATION-1) — so it is **specified, not an open question**.
- **(c) The advisory-token scope (Q2 / HIST-Fold-4).** The reused blanket `advisory-vocabulary` lint forbids the `decision` token as system output, but the human-committed region legitimately concerns the CON-BR4 "decision" concept. NFR-Requirements is the natural point to pin the lint tier — Q2 decides whether that is **namespace-distinct wording that avoids the token** (reuse the lint unmodified) or a **system-output-scoped lint block** (new mechanism, honors the literal "Underwriter's decision" heading), or a **one-stage deferral to NFR-Design**.
- **(d) The `rule_results` disclosure pattern (Q3).** The FD left it shape-only; NFR-tier testability needs a concrete, faithful pattern. The binding constraint (INV-FAITHFUL / BR-HIST-5): **no entry may be absent from the DOM** — so any collapse must be **visibility-only** (entries remain mounted), letting T6 assert all N entries are present regardless of state. Q3 pins the pattern.

The state machine (T14) covers per-state renders + one consolidated transition test on the same double (the `ui-memo-view` precedent).

### Q1 — Shape of the dual-READ capturing double (both ops are reads; no read+write asymmetry)  *(user-flagged)*
The write-path units (U7/U8) used an **asymmetric** double — a read op (`fetchContext`) + a write op (`submit*`) — whose load-bearing teeth were "**zero submit calls before Confirm**" (NOFINAL/CONFIRM/CANCEL). `ui-history` has **two reads** (`fetchList`, `fetchDetail`) and **no write**, so there is no "zero-before-X" write gate to construct. How is the double shaped, and what replaces the write-gate cross-guard?

- **A. One injected `historyFetchSeam` double exposing BOTH reads as independently-capturing spies, constructed ONCE per suite** *(Recommended)*.
  `{ fetchList, fetchDetail }` where each is a programmable capturing spy recording its own args + call-count (`fetchList.calls[i] = [page, size]`, `fetchDetail.calls[i] = [decision_id]`), each sequenceable (`resolveWith` / `rejectWith`) — the single-double-per-suite precedent (ui-queue Fold-1 / ui-memo-view Fold-1), adapted for two reads. **The cross-guards become read-attribution + call-count teeth**, not a write gate: **T5** (a select hits `fetchDetail` only; a page change hits `fetchList` only), **T13** (Back adds **zero** new `fetchList` calls; page/items identical), **T10** (listError Retry → `fetchList(lastPage)`; detailError Retry → `fetchDetail(sameId)`). No "zero-before-confirm" teeth is needed or constructed — its analog here is **"Back triggers zero new list fetches"** + **"each retry targets the correct op with the correct arg."** Matches the FD's single injected `historyFetchSeam` object.
- **B. Two separate doubles (one for list, one for detail), injected independently.** More isolated, but the FD's `historyFetchSeam` is **one** object owning both reads (BR-HIST-4); two doubles make "the same seam owns both reads" harder to assert as a single object and diverges from the one-double-per-suite precedent. *(Rejected — contradicts the single-seam FD.)*
- **C. Global `fetch` / URL interceptor (MSW-style).** More realistic, but capturing the exact `page` / `decision_id` for the retry/back teeth is indirect (the siblings rejected this for the same reason). *(Rejected.)*

`[Answer]:` A — one injected `historyFetchSeam` double exposing both reads as independently-capturing spies, constructed once per suite. The cross-guards become **read-attribution + call-count teeth** (a select hits `fetchDetail` only; a page change hits `fetchList` only; Back adds zero new `fetchList` calls; each retry targets the correct op with the correct arg) rather than a write-gate — there is **no "zero-before-confirm" analog needed** since both operations are reads.

### NFR-HIST-Fold-1 (check i) — Q3's "collapse via `hidden`, never unmount" a11y + query nuance — **CLEAN**
Two facts reconcile faithfulness (DOM-present) with a11y (not announced when collapsed):
- **The collapse mechanism** must be the HTML `hidden` attribute (or `display:none`), which **removes the collapsed subtree from the accessibility tree** — so a screen reader does **not** announce collapsed `rule_results` entries. **No separate `aria-hidden` is needed** (it would be redundant with `hidden`/`display:none`; `visibility:hidden`/`aria-hidden`-alone are **not** used). Collapsed entries remain **mounted** in the DOM (INV-FAITHFUL).
- **T6's faithfulness assertion must therefore use a DOM-level query** — `getAllByTestId('history-detail-ruleresult-<i>')` / `container.querySelectorAll(...)`, which **find mounted-but-hidden nodes** — **not** a visibility-filtering `getByRole`/`getByText` query (RTL's role/text queries ignore `hidden` by default and would miss collapsed entries, producing a false faithfulness failure).
- **Resolution:** add a T6 acceptance criterion pinning **(a)** collapse via `hidden`/`display:none` (a11y-tree-removing, no `aria-hidden`) and **(b)** a DOM-level testid query for the "all N present" assertion. Detailed a11y (focus management, announce-on-expand) stays **soft/non-gating** (T17) and its full verification is deferred to Code-Gen. Recorded in `nfr-requirements.md` (T6 acceptance) + `tech-stack-decisions.md`. **No gap.**

### NFR-HIST-Fold-2 (check ii) — Q1's single-double vs T13's Back-preserve "call-count unchanged" — **CLEAN (a simple before/after snapshot suffices)**
T13 asserts **Back adds zero new `fetchList` calls**. This does **not** require the double to distinguish before-vs-after-mount calls: within the **single** T13 test the assertion is a **before/after snapshot** of `fetchList.calls.length` taken **immediately before and immediately after** the Back action, and asserted equal (plus `page`/`items` identical).
