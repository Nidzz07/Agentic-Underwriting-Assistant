## 3. Functional-Design questions — Q1–Q7 (full text + filled answers, all **A**)

- [x] Questions surfaced, answered by the user (2026-07-09), and embedded here per the standing convention.

### Q1 — Depth confirmation
**A.** Lighter (display) **+ async-state addendum**. · **B.** Plain lighter. · **C.** Bump to standard/comprehensive.
**[Answer]: A** — lighter (display) holds (ui-queue owns no business logic of its own); the loading/error/empty/ready
lifecycle (the first real WIRE-1 fetch) is a new behavioral concern called out explicitly in the FD, without bumping the
unit to comprehensive.

### Q2 — Queue list/table primitive (ui-shell has **no** list/table primitive)
**A.** Local presentational list/table component in `frontend/src/queue/` composing `Panel` + badges; **ui-shell stays
frozen**. · **B.** Promote a generic list/table primitive **into `ui-shell` now** (amends a frozen unit). · **C.**
Semantic `<table>` inline in a `Panel`, no reusable component.
**[Answer]: A** — ui-queue defines its own local presentational list/table component inside `frontend/src/queue/`,
composing `Panel` + `RecommendationBadge`/`ConfidenceBadge` per row; ui-shell stays frozen/untouched. Promotion to a
shared primitive is revisited later **only if** reuse across ui-history/ui-memo-view actually materializes — don't design
for a hypothetical now.

### Q3 — The three async states (real WIRE-1 fetch lifecycle)
**A.** Four explicit states — `loading` (skeleton rows), `error` (`error.message` + Retry; no raw `error.detail`),
`empty` (`items:[]`/`total:0` → distinct "No applications" message), `ready` (table). · **B.** Three states, empty as a
zero-row table. · **C.** Single not-ready state.
**[Answer]: A** — four explicit render states: **loading** (skeleton/placeholder rows), **error** (surface
`error.message` + a **Retry** affordance; never leak `error.detail` internals raw to the user), **empty**
(`items:[]`/`total:0` → a distinct "No applications in the queue" message), **ready** (the table). **Sub-decision**:
surface **`message`** to the user; expose **`code`** via a `data-testid`/console binding for test assertion, **not** in
the visible UI text.

### Q4 — Nullable recommendation/confidence rows
**A.** Neutral **"pending / not yet drafted"** placeholder cell (no badge). · **B.** Hide not-yet-scored rows. · **C.**
Distinct "Pending" pseudo-badge.
**[Answer]: A** — render a neutral "pending / not yet drafted" placeholder cell (no badge) for null
recommendation/confidence rows; the queue shows **all** applications including not-yet-scored ones, mirroring WIRE-1's
`MemoView status: pending` pattern.

### Q5 — Row selection / navigation (no app router defined yet)
**A.** Row emits a **selection affordance** (`onSelect(application_id)`); route target/wiring **deferred**. · **B.**
ui-queue owns navigation to the memo view (R4). · **C.** No navigation at all.
**[Answer]: A** — each row exposes a selection affordance (e.g. emits `onSelect(application_id)`); the actual route
target/wiring is deferred as a shell/router concern for later integration. ui-queue only emits the selection event.

### Q6 — Pagination controls (WIRE-1 R2 offset/limit; PER-1)
**A.** Include pagination behavior (prev/next + current-page/total) consuming the `page` wrapper. · **B.** First page
only; defer pagination.
**[Answer]: A** — include pagination behavior (prev/next + current-page/total indicator) consuming the `page` wrapper;
PER-1 makes paging core to the queue and the wrapper already exists in WIRE-1.

### Q7 — RoleGate usage in the queue (R2 = authenticated any-role; all roles hold `VIEW_QUEUE`)
**A.** View-only for all roles; **no RoleGate at row level**. · **B.** Underwriter-only "act" affordance via
`RoleGate(can="act")`.
**[Answer]: A** — the queue is view-only for all roles; no RoleGate at row level; the act/commit path lives entirely in
ui-approval-gate/ui-override-form, keeping the queue a pure read view.

## 4. Ambiguity-check (RUN 2026-07-09) — grounded on the frozen surfaces above

- [x] Ran the mandatory ambiguity-check against the seven answers + the frozen contracts (ui-shell primitives/copy/
  tokens/session; WIRE-1 R2 route + ApplicationSummary shape + list-wrapper/error envelopes; auth-rbac Role). All folds
  are **resolvable against the frozen contracts** (no improvisation) → **no hard STOP before the plan gate**; two folds
  are surfaced below for your review **at the plan gate** (one CLEAN, one carries a pin you may override).

### Fold-A (your check i) — local list/table `data-testid` consistency vs `ui-shell` — **CLEAN**
`ui-shell` §6 establishes the convention **`shell-<primitive>-<purpose>`** for shell primitives and states *"views pass a
`data-testid` where they assert."* The convention is a **shape** (`<area>-<element>-<purpose>`), and the `shell-` prefix
is scoped to shell primitives — so a **view** supplies its own namespaced testids. Resolution (no gap): `ui-queue`'s local
component adopts the **analogous** shape namespaced to the view — e.g. `queue-table`, `queue-row`,
`queue-row-<application_id>`, `queue-state-loading` / `queue-state-error` / `queue-state-empty`, `queue-error-code` (the
hidden `code` binding from Q3), `queue-pagination-prev` / `queue-pagination-next`, `queue-page-indicator`. This is
**applying** the established convention, not inventing one; the exact literal strings + a lint/test assertion (BR-UI-5
analogue) are pinned in Part 2 `business-rules.md` / enforced at NFR/Code-Gen. **No frozen artifact touched.**

### Fold-B (your check ii) — Retry re-fetch semantics — **PINNED at FD (position-preserving); mechanics → Code-Gen**
Q3-A's **Retry** implies one behavioral decision: on a failed fetch of page *N*, does Retry re-request **page *N*
(last-viewed)** or reset to **page 1**? Grounded call — **pin the behavioral contract now** (it is part of the
async-state model that §2 made a first-class FD concern), leave the mechanics to Code-Gen:
- **Pinned (FD behavior)**: Retry **re-requests the last-requested page** — it re-attempts the exact fetch that failed,
  preserving the user's position; it does **not** reset to page 1. (Initial-load failure ⇒ last-requested page *is* page
  1, so Retry there naturally re-fetches page 1.)
- **Deferred (Code-Gen)**: *how* the current page is held in state (hook/store shape), retry debounce/throttle, and any
  request-cancellation are implementation mechanics — not FD.
- **This pin is flagged for your confirmation at the plan gate** — if you'd rather Retry reset to page 1, or leave the
  page-vs-1 choice entirely to Code-Gen, say so and I'll amend before Part 2.

### Grounded notes (non-gaps — recorded so they are not silently assumed)
- **N1 — pending atomicity (Q4)**: `ApplicationSummary`'s `recommendation` / `confidence` are treated as **co-present or
  co-null**, because `rules_engine.RuleResultReport` always carries **both** a `recommendation` and a `confidence` when a
  recommendation is drafted. So "pending" = all three (`recommendation_id`/`recommendation`/`confidence`) null; a
  partial-null row is not an expected WIRE-1 state. (If the backend ever emits a partial, the pending placeholder still
  renders safely.) No gap.
- **N2 — default page size (Q6)**: WIRE-1 R2 takes `?page=&size=`; the **default `size`** is a tuning **value** (PER-1
  related) deferred to NFR-Design / Code-Gen — consistent with `ui-shell` deferring token *values*. FD pins the paging
  **behavior/shape**, not the numeric default. No gap.
- **N3 — namespace safety**: the queue renders **system** `Recommendation` values (UPPERCASE, incl.
  `DECLINE-RECOMMEND` — never a bare `DECLINE`) via `RecommendationBadge`; it never renders a human `CommitAction`
  (`approve`/`override`) — the queue is read-only and has no commit affordance (Q7-A). No namespace collision. No gap.
